# Тестовая матрица dsh-kanban

## Модульные тесты

Идут без харнесса, без сети и без `node_modules`:

```bash
npm test
```

| Файл | Что покрывает |
|---|---|
| `test/config.test.mjs` | значения по умолчанию, скалярность всех полей настроек, метки и пределы колонок |
| `test/order.test.mjs` | дробный индекс: деление между соседями, тысяча вставок в одно место, сортировка обычным сравнением строк |
| `test/store.test.mjs` | хранилище: порядок, перенос без переписывания соседей, журнал переходов, поиск по сессии, переоткрытие базы |

## Ручные сценарии на живом харнессе

| Сценарий | Ожидание |
|---|---|
| Установка с нуля | Плагин виден, карточка настроек на месте |
| Загрузка плагина | В журнале `dsh-web.service` нет строки `failed to apply loader entry dsh-kanban` |
| Совпадение имени пакета | Обе проверки curl ниже проходят |
| Раздел доски | «Задачи» открывается, шесть колонок в порядке воркфлоу |
| Ненастроенный Gitea | Импорт объясняет причину, а не показывает пустой список |
| Настроенный Gitea | Список открытых issue приходит, pull request в нём нет |
| Импорт issue | Карточка с заголовком, телом, метками и ссылкой |
| Повторный импорт | Уже импортированный issue помечен |
| Перетаскивание | Порядок держится после перезагрузки, в журнале запись с источником `manual` |
| Предел колонки | Превышение подсвечено, перенос выполнен |
| Запуск задачи | Чат с выбранной моделью, первое сообщение с текстом issue, карточка в «В работе» |
| Две задачи сразу | Две независимые сессии |
| Чип в чате | Виден в сессии с доски, отсутствует в обычной |
| Смена колонки из чипа | Отражается на доске и в журнале |
| Смена языка | Доска, карточка и чип перерисовываются без перезагрузки |
| Перезапуск харнесса | Задачи и порядок на месте |
| Выгрузка плагина | Маршруты сняты, база закрыта, ошибок в журнале нет |
| Автоперемещение | Закрытый issue без ветки уезжает в Done с пояснением в журнале |
| **Закрытие issue в Gitea** | После переноса карточки в «Выполнено» открыть issue в Gitea и убедиться, что он ЗАКРЫТ. Меток колонок доска не ставит — их присутствие или отсутствие ничего не проверяет |
| Вебхук без подписи | Отвергается кодом 401 |
| Конфликт | Двинуть карточку на доске и одновременно изменить issue; проигравшая сторона названа в журнале задачи |

## Проверка совпадения имени пакета

Расхождение имени в трёх местах НЕ даёт ошибки в журнале: серверная половина работает, интерфейса нет.

```bash
curl -s http://127.0.0.1:3080/ | grep -c '@goodandready/dsh-kanban'
```

Ожидание: больше нуля.

```bash
curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:3080/plugins/@goodandready/dsh-kanban/client.js'
```

Ожидание: `200`.

## Проверка маршрутов

```bash
curl -s 'http://127.0.0.1:3080/dsh-kanban/board?board=main'
```

Ожидание: JSON с шестью колонками.

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'sec-fetch-site: cross-site' 'http://127.0.0.1:3080/dsh-kanban/task'
```

Ожидание: `403`.

## Проверка на чистом ядре

Плагин обязан импортироваться тем ядром, которое стоит на машине. Именованный
импорт того, чего ядро не отдаёт, — ошибка разбора: падает не плагин, а
загрузка ВСЕГО дерева плагинов, и харнесс уходит в цикл перезапусков. Так
`settingsNamespace`, убранный в `dsh-v0.1.2-alpha.2`, положил прод целиком
(#145, #144).

Проверка идёт из профиля, чтобы имена ядра разрешались так же, как у харнесса:

```bash
cd "$DSH_HOME/profiles/web"
node -e "import('@goodandready/dsh-kanban').then(m => console.log('ok', m.SETTINGS_NAMESPACE))"
node -e "import('@deepseek-ai/dsh-settings').then(m => console.log(Object.keys(m).join(',')))"
```

Первая команда обязана напечатать `ok dsh-kanban`. Вторая показывает, что ядро
действительно отдаёт, — по ней видно, на что опираться нельзя.

Ожидаемые версии ядра — от `0.1.0-rc.6` до любой `0.x`, включая предвыпуски
`0.1.1-rc.*` и `0.1.2-alpha.*`; ровно это записано в `peerDependencies`.

## Замер префиксных маршрутов

Префиксные маршруты регистрируются БЕЗ завершающего слэша: со слэшем
сопоставление сводится к равенству пути, и всё, что глубже, уходит в статику,
отвечая пустым телом. Пустое тело в ответе — верный признак, что маршрут не
сопоставился: свои отказы плагин отдаёт JSON.

```bash
for p in /dsh-kanban/task /dsh-kanban/task/abc/log /dsh-kanban/session/abc/task; do
  printf '%-32s -> ' "$p"
  curl -s -m 8 -w ' [%{http_code}]' "http://127.0.0.1:3080$p"; echo
done
```

Ожидание: у каждого пути тело JSON, а не пустая строка.

## Проверка после deploy

Установка из worktree релизной проверкой не считается: проверяется релизный артефакт. В issue фиксируются SHA `main`, версия, время, результаты health и smoke, состав релиза и cleanup.
