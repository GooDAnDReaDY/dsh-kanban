# dsh-kanban

Доска задач для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness): задачи из Gitea, колонки по реальному воркфлоу и отдельная сессия агента под каждую задачу.

## Что умеет

- **Ставить задачи и следить за ними.** Свои задачи и задачи из Gitea на одной доске, порядок карточек переживает перезагрузку.
- **Заводить задачу из issue.** Кнопка «+ Задача» показывает открытые issue выбранного репозитория; уже импортированные приглушены. Карточка заполняется заголовком, телом, метками и ссылкой.
- **Запускать работу.** Выбрали модель, нажали «Начать» — поднимается отдельная сессия агента по этой задаче, карточка уезжает в «В работе».
- **Продолжать в том же чате.** У задачи ровно одна сессия на всю её жизнь. Как только сессия есть, кнопка становится «Продолжить» и открывает прежний чат, а не заводит новый. Перед отправкой видно заготовку сообщения — её можно переписать, уйдёт то, что осталось в поле.
- **Показывать задачу в чате.** В сессии, поднятой с доски, в шапке виден чип задачи с текущей колонкой.

## Установка

```bash
dsh plugin --profile web add @goodandready-private/dsh-kanban
```

Из локальной рабочей копии:

```bash
dsh plugin --profile web add file:/путь/к/dsh-kanban
```

Перезапустите веб-интерфейс и обновите страницу с очисткой кэша.

Других плагинов не требует: клиент Gitea у канбана свой. Пока адрес инстанса не задан, доска работает, а импорт честно объясняет, чего не хватает.

## Настройка

**Настройки → Плагины**, карточка **Канбан**.

| Поле | Что задаёт |
|---|---|
| Адрес инстанса | `https://gitea.example.com`. Пусто — импорт недоступен. |
| Имя учётной записи | ИМЯ учётной записи DSH с токеном, по умолчанию `GITEA_TOKEN`. Сам токен сюда не вводить. |
| Корень проектов | Где лежат рабочие копии. Пусто — рабочая папка харнесса. |
| Шаблон первого сообщения | Текст, с которого начинается сессия. Пусто — встроенный. Подстановки: `{repo}`, `{issueNumber}`, `{title}`, `{body}`, `{issueUrl}`. |
| Метки колонок | Имя метки Gitea для «В работе», «Ревью», «Deploy», «Cleanup». Пусто — метка не ставится. |
| Пределы колонок | Предел числа карточек. Ноль — без предела. |

Токен в настройках **не хранится**: там только ИМЯ учётной записи, а сам секрет лежит в хранилище учётных данных DSH. Наружу значение не отдаётся никогда, включая сообщения об ошибках. Если у вас уже настроен `GITEA_TOKEN` для других плагинов, достаточно вписать адрес инстанса.

Все поля настроек скалярные. Это не упрощение, а требование: клиентский API настроек пишет только скаляры, и словарь или массив сделал бы карточку нередактируемой. Доски поэтому живут в хранилище задач, а не в настройках.

## Колонки

| Колонка | Признак входа |
|---|---|
| Backlog | issue есть, никто не взял |
| В работе | сессия поднята, в issue есть стартовый комментарий с планом и веткой |
| Ревью | PR снят с WIP, ревьюер даёт PASS/FAIL |
| Deploy | PR влит в `main`, ждём согласованный deploy и production-проверку |
| Cleanup | ветка в Gitea, worktree и локальная ветка ещё не удалены |
| Done | issue закрыт **и** cleanup записан в итоговом комментарии |

Колонка `cleanup` не лишняя: по воркфлоу задача не завершена, пока cleanup не сделан и не записан. Доска, отправляющая карточку в `done` по merge, врёт ровно там, где копятся забытые ветки.

WIP PR **не** двигает карточку в «Ревью»: он открывается рано и означает «работа идёт», а не «смотрите».

Превышение предела колонки подсвечивается, но перенос не запрещает: предел — ориентир, а не преграда.

## Чего плагин не делает

- **Не создаёт ветки и worktree.** По воркфлоу агент сначала делает preflight — смотрит открытые ветки и worktree, проверяет рабочее дерево — и только потом заводит worktree от свежего `origin/main`. Ветка, созданная заранее, обессмысливает preflight.
- **Не пишет стартовый комментарий в issue.** Его пишет агент после preflight, потому что до preflight ветка и план неизвестны.
- **Не подсказывает имя ветки** в первом сообщении: его выбирает агент.
- Ветка и worktree на карточке — **наблюдение**, а не намерение.
- Не трогает Hermes Kanban. Это другая система.

## Хранилище

`<DSH_HOME>/kanban/kanban.db`, где `DSH_HOME` — переменная окружения либо `~/.dsh`. SQLite через встроенный `node:sqlite`; внешних зависимостей нет.

Порядок карточек хранится дробным индексом: перетаскивание — всегда один `UPDATE` одной строки, сколько бы карточек ни было в колонке.

## Автоперемещение

**Обратно в Gitea доска сообщает одно: закрытие issue**, когда карточка доходит до «Выполнено». Меток колонок она не ставит — стадия и так видна по ветке и pull request, а метка лишь пересказывала бы то, что уже написано рядом. Заодно доска не трогает чужую разметку вовсе.

Карточки двигаются сами. Три источника со строгим приоритетом — **Gitea > инструмент агента > жизненный цикл сессии**. Без приоритета «PR влит → deploy» через секунду перебивалось бы «ход завершился → в работе», и карточка прыгала бы.

| Наблюдение в Gitea | Колонка |
|---|---|
| есть ветка по задаче | В работе |
| PR открыт и снят с WIP | Ревью |
| PR влит | Deploy |
| issue закрыт, ветка ещё есть | Cleanup |
| issue закрыт, ветки нет | Done |

Метки и заголовок доска забирает из Gitea при каждой сверке: переименовали issue или сменили `priority/high` на `priority/critical` — доска это увидит. **Тело не забирает** — его правит человек заметкой из чипа, и сверка, затирающая тело каждые две минуты, съедала бы заметки; тело обновляется по кнопке «обновить».

Каждый переход попадает в журнал задачи с источником и пояснением: `Ревью ← gitea · PR #39 снят с WIP`. Когда доска однажды покажет не то, будет видно, кто её подвинул.

### Две доски

Досок ровно две, и обе заводятся сами при первом запуске.

| Доска | Колонки | Для чего |
|---|---|---|
| Проектная | бэклог · в работе · ревью · deploy · cleanup · выполнено | задачи из issue |
| Простая | бэклог · в работе · проверка · выполнено | свободные задачи |

`review`, `deploy` и `cleanup` осмысленны только там, где за задачей стоит issue: у свободной заметки нет ни ветки, ни PR, и Gitea о ней ничего не скажет. Три колонки, которые никогда не заполнятся, — не запас на будущее, а помеха.

Импорт issue на простую доску не предлагается и отвергается сервером. Вид доски — её явное свойство, а не вывод из содержимого: доска, меняющая число колонок от того, что на неё положили, ведёт себя непредсказуемо.

Прежняя единственная доска СТАНОВИТСЯ проектной вместе со всеми задачами — вторая заводится рядом, а не вместо неё. Смены вида у доски с задачами пока нет: карточки из `deploy` и `cleanup` на простой доске девать некуда.

### Чип задачи в чате

В шапке чата, поднятого с доски, виден чип задачи с текущей колонкой. Он умеет три вещи:

- **перенести в колонку** — то же, что перенос на доске, со всеми последствиями;
- **перейти к карточке** — открывает доску и сразу окно этой задачи, переключая доску, если карточка лежит на другой;
- **оставить заметку** — дописывает текст в тело задачи.

Заметка меняет тело, а тело уходит агенту первым сообщением при запуске. Значит заметка, оставленная до запуска, попадёт в работу, а после запуска — нет; это написано подсказкой рядом с полем, иначе поведение выглядит случайным.

Дописывает заметку сервер, а не браузер: чип держит копию задачи, и склейка у него потеряла бы всё, что тело нажило с момента её получения.

### Создание задачи: проект или не проект

```
Новая задача
  ○ Проект        → репозиторий: выбрать из Gitea либо ввести имя нового
  ○ Не проект     → уходит на простую доску
```

**Проект** заводит issue в Gitea, и карточка сразу к нему привязана. Репозиторий выбирается из существующих либо создаётся: приватный и пустой, без README и заготовок. Создание репозитория необратимо, и окно говорит об этом до нажатия, а не после.

**Не проект** — заметка, не относящаяся ни к какому репозиторию: живёт на простой доске и в Gitea не попадает.

Правило без исключений: **есть issue — проектная доска, нет — простая.** Помнить, где вы её завели, не нужно.

Порядок при создании неслучаен: сперва репозиторий, потом issue, потом карточка. Обрыв на середине не оставляет карточку привязанной к репозиторию без issue — лучше не завести её вовсе и сказать об этом. Созданный репозиторий при этом не удаляется: убирать чужое добро из-за своей неудачи хуже, чем оставить лишний пустой репозиторий.

**Инструмента заведения issue у агента нет и не будет.** У соседнего плагина `dsh-gitea` уже есть `gitea_issue_create`, и второй способ делать то же самое разошёлся бы с первым. Агент зовёт свой инструмент, а карточка приезжает подхватом.

### Задачи приезжают сами

В настройках — список репозиториев через запятую (`владелец/репо` либо просто `репо`). Доска забирает оттуда открытые задачи и заводит карточки в бэклоге.

**Пустой список означает «не забирать ниоткуда», а не «забирать всё».** Первый же запуск с незаполненной настройкой залил бы доску всеми открытыми issue организации.

Не берутся: закрытые issue (это уже не работа), pull request-ы (это ход работы, а не сама работа), issue с уже заведённой карточкой и те, чью карточку вы **удалили** — удаление значит «видеть её здесь не хочу», и возвращать её каждый проход было бы спором с человеком каждые две минуты.

Вебхук зовёт подхват для того репозитория, о котором пришло событие: новый issue становится карточкой за секунды, а не ждёт таймера. Только по репозиторию события — полный обход при каждом чихе в любом из отслеживаемых означал бы обращение ко всем.

Недоступный репозиторий не роняет остальные: он пропускается до следующего прохода, а причина попадает в состояние сверки в шапке.

### Архив

Карточки, отстоявшие свой срок в «Выполнено», уезжают в архив — свой экран, а не колонка: колонка это стадия работы, а архив стадией не является. Срок в настройках, по умолчанию неделя, ноль отключает.

Возраст считается с попадания карточки в «Выполнено», а не по последнему изменению: сверка трогает задачу и после завершения, и по «изменено» архив откладывался бы бесконечно.

**Архивируется только `done`.** Задача, застрявшая в ревью на месяц, — это сигнал, а не мусор, и прятать её нельзя.

Ничего не удаляется: возвращённая карточка встаёт в ту же колонку, откуда ушла. Архив обязан быть обратимым, иначе им не станут пользоваться из страха.

### Перенос без мыши

На карточке — «перенести» со списком колонок её доски. Окно подтверждения и последствия те же, что при перетаскивании: путь другой, а результат один, и разойтись им нельзя. Карточка стала точкой табуляции — доска была мышиной целиком.

Перетаскивание никуда не делось: речь о втором пути, а не о замене.

### Видно, как идёт сверка

В шапке доски — состояние сверки с Gitea:

| Что видно | Что значит |
|---|---|
| `сверено 2 мин назад` | всё в порядке; точное время в подсказке |
| `сверяемся с Gitea…` | проход идёт прямо сейчас |
| `сверки с Gitea ещё не было` | харнесс только поднялся |
| **`сверка не проходит`** | выделено; в подсказке место, причина и время последней удачной сверки |

Причина называется словами — «репозиторий не найден», «токен не подошёл», — а не прячется в журнал харнесса. Доска, переставшая обновляться, не имеет права молчать: отличить «ничего не изменилось» от «мы ослепли» иначе нечем.

**Неудача не затирает время последнего успеха.** Иначе теряется ответ на главный вопрос: когда доска в последний раз видела правду.

Состояние живёт в памяти процесса, а не в базе: это положение текущего запуска. После перезапуска честнее сказать «сверки ещё не было», чем показать вчерашний успех как сегодняшний.

Повторных попыток и починки здесь нет — задача показать, а не вылечить.

### Отборы

В шапке доски — по одному списку на репозиторий и на каждое пространство меток:

```
[ репозиторий ▾ ] [ type ▾ ] [ priority ▾ ] [ status ▾ ] [ scope ▾ ] ...   [ поиск ]
```

| Уровень | Правило |
|---|---|
| между пространствами | **и** — «срочные баги» это `priority/high` и `type/bug` |
| внутри пространства | **или** — срочность у задачи одна, и «и» всегда давало бы пусто |

Пространства собираются из меток, которые реально лежат на карточках: всё до первой `/` — пространство, всё после — значение. Список не зашит, поэтому заведённое в Gitea новое пространство появится само, без правки кода и без релиза. Порядок задан для известных, незнакомые дописываются в конец по алфавиту.

Метки без пространства (`epic`, `hotfix`) своего отбора не получают — список из двух значений ради двух меток был бы мебелью. На карточках они видны и находятся поиском.

**Счётчик колонки считает отобранное, а поиск — нет.** Разница осмысленная: поиск временный, и предел «3 из 3» при одной найденной карточке врал бы; отбор постоянный, и на отборе по одному проекту «в работе 3 из 3» должно значить «по этому проекту».

Отборы держатся, пока открыт харнесс, и сбрасываются при смене доски: на другой доске те же значения могут не встречаться вовсе.

### Возврат в чат

В шапке доски слева — кнопка «В чат». Доска открывается на месте разговора, и до неё закрыть её можно было тремя неочевидными способами: клавишей Escape, повторным щелчком по строке в боковом списке и переходом в чужую сессию. Кнопка не заводит четвёртого механизма, а зовёт тот же самый: разойтись им негде.

### Карточка открывается окном

Панель справа в 420 пикселей вмещала описание и журнал, но не план с отметками. Теперь карточка открывается окном поверх доски: описание, метки, ссылка на issue, план агента, журнал переходов, время, пусковая полоса. Закрывается крестиком, щелчком по затемнению и клавишей Escape.

Окно живёт внутри экрана доски, а не поверх всего интерфейса: доска сама лежит в колонке разговора, и выход за её пределы наложился бы на чужие части оболочки. Снизу оставлен запас — поверх интерфейса висят плавающие виджеты соседних плагинов.

### Время на доске

| Где | Что видно |
|---|---|
| карточка | сколько стоит в этой колонке — `здесь 3 дн` |
| карточка с сессией | когда её последний раз трогали; после порога молчания отметка становится тревожной |
| окно задачи | когда заведена и когда менялась в последний раз |

Формат относительный, потому что «третий день» читается мгновенно, а точная дата требует сравнения с сегодняшним числом; сама дата — в подсказке при наведении. Время в колонке считается по отметке, которую ставит перенос: перестановка внутри колонки её не сбрасывает, задача в ревью третий день там и остаётся.

Порог молчания настраивается (`staleAfterMin`, по умолчанию час) и считается на хосте: отдавать браузеру ещё и порог значило бы отдавать ему решение. Отдельного опроса живости сессий нет — это был бы второй источник правды и лишняя нагрузка.

**Открыть чат.** У задачи с сессией в окне есть кнопка возврата в её чат. Без неё задача, идущая вторые сутки, ищется в общем списке по имени вида `kanban-9e84cae6-…`.

### Сворачивание колонок

Шесть колонок по 220 пикселей не помещаются на ноутбуке. Поэтому пустая колонка сама сжимается до вертикальной полоски с названием, а щелчок по названию сворачивает и разворачивает любую, включая непустую. Решение человека сильнее автоматики в обе стороны: развёрнутая им пустая колонка не схлопнется у него на глазах.

Свёрнутая показывает число карточек — колонка с работой, выглядящая пустой, хуже любой тесноты. Целью переноса она остаётся: карточку можно бросить в неё, не разворачивая.

Колонки не прячутся совсем. `cleanup` пуст ровно до того момента, когда в нём появляется забытая ветка; спрятав его, мы спрятали бы тот самый сигнал, ради которого его завели.

### Ручной перенос — это команда агенту

Карточку двигают не ради учёта. Человек перетащил — значит просит запустить тот этап, куда перетащил, и команда уходит в чат задачи отдельным сообщением. При отпускании карточки доска показывает окно с описанием последствий; отмена оставляет карточку на месте.

| Куда перенесли | Что происходит |
|---|---|
| Backlog | работа останавливается: идущий ход агента прерывается |
| В работе | агент начинает или продолжает реализацию |
| Ревью | агент снимает с PR пометку черновика и запрашивает проверку |
| Deploy | агент вливает PR и выкатывает |
| Cleanup | агент удаляет ветку, worktree и локальную ветку |
| Done | завершение; сюда переносит только человек |

**Перенос в Deploy и есть явное «ок» на выкатку.** Воркфлоу требует разрешения человека перед deploy, и это разрешение дано движением, а не словом в чате — второй раз агент не спрашивает.

Инструменту агента переход в `done` закрыт и даже не предлагается в перечислении. Его путь к завершению — закрыть issue и удалить ветку; сверка с Gitea сама увидит закрытый issue без ветки. Карточка двигается фактом, а не заявлением.

### План агента на карточке

Агент публикует план своим инструментом `board_plan` — доска не разбирает его сообщения, потому что разбор это гадание, и не опирается на чужой `todo_list`, потому что это была бы зависимость от соседнего плагина.

Список пунктов шлётся один раз, дальше агент двигает только номер текущего: гонять весь план ради одного числа незачем. Всё, что до текущего пункта, считается сделанным.

На карточке видно `3 из 7 · пишу тесты`, в окне задачи — весь план: сделанное зачёркнуто, идущий пункт выделен. Плана из одного пункта и плана из двадцати это касается одинаково — на карточку едут только числа и текущий пункт.

| Состояние | Откуда известно |
|---|---|
| в работе | у живого агента идёт ход |
| ждёт пользователя | запрос разрешения или вопрос |
| остановился | сессия у задачи записана, а живого агента за ней нет |

«Остановился» — не догадка по тишине, а факт: так выглядит работа, прерванная перезапуском харнесса. Порога тишины в настройках нет и не будет: он был бы догадкой там, где есть точный признак.

**Признак «нужен человек».** Колонки «Блокировано» в наборе нет, поэтому запрос разрешения или вопрос агента не двигают карточку, а поднимают на ней оранжевую точку. Признак снимается сам, когда ход возобновляется.

**Инструмент агента** `board_move` выключен по умолчанию: скилл `gitea-project-workflow` пока запрещает этому CLI трогать канбан.

Определение инструмента живёт в `lib/board-tool.js` отдельно от обвязки cordis и
следует контракту `defineTool` из `@deepseek-ai/dsh-tools` **не ниже 0.1.0-rc.8**:
`output` обязателен, а `parameters` — карта «имя -> схема значения», а не JSON
Schema с корнем `type: 'object'`. Пропущенный `output` роняет не инструмент, а
загрузку всего профиля, поэтому форма закреплена тестами `test/board-tool.test.mjs`.

## Синхронизация

**Gitea → канбан.** Опрос с настраиваемым промежутком плюс вебхук для мгновенной сверки. Вебхук — ускорение, а не замена: он может быть не настроен, недоступен снаружи или потерян, и опрос остаётся всегда.

Маршрут вебхука `/dsh-kanban/webhook`, подпись проверяется общим секретом. **Без секрета вебхук не принимается вовсе** — иначе карточки двигал бы кто угодно снаружи.

**Канбан → Gitea.** Перенос карточки ставит метку колонки, `Done` дополнительно закрывает issue. Чужие метки не трогаются: `bug`, `feat`, `hotfix` принадлежат процессу, и стирать их доска права не имеет. Свои метки `kanban/*` заводятся автоматически, если их в репозитории ещё нет.

Отправка идёт очередью: перенос карточки не ждёт сети, доска работает и при недоступном Gitea. Неудачная отправка повторяется, а исчерпав попытки — попадает в журнал задачи, а не исчезает.

**Конфликты.** Если обе стороны изменились с последней сверки, побеждает более позднее изменение, а проигравшее **называется в журнале задачи**. Синхронизация, тихо отменяющая правку человека, хуже отсутствующей: расхождение остаётся, а узнать о нём неоткуда.

До первой сверки «изменилось с прошлого раза» смысла не имеет — прошлого раза не было, — поэтому первая сверка принимает положение дел, а не спорит с ним.

## Ограничения

- Точного «работа идёт прямо сейчас» инстанс не знает. Порядок репозиториев и вывод колонок — приближение по открытым задачам, веткам и времени правки.
- Клиент Gitea покрывает только нужное доске: issue, PR, ветки, метки, поиск репозиториев.
- Неполное наблюдение считается отсутствующим: репозиторий, который не прочитался целиком, пропускается до следующей сверки. Иначе непрочитанные PR выглядели бы как их отсутствие и утаскивали карточку назад.
