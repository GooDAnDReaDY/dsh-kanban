# dsh-kanban

Доска задач для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness): задачи из Gitea, колонки по реальному воркфлоу и отдельная сессия агента под каждую задачу.

## Что умеет

- **Ставить задачи и следить за ними.** Свои задачи и задачи из Gitea на одной доске, порядок карточек переживает перезагрузку.
- **Заводить задачу из issue.** Кнопка «+ Задача» показывает открытые issue выбранного репозитория; уже импортированные приглушены. Карточка заполняется заголовком, телом, метками и ссылкой.
- **Запускать работу.** Выбрали модель, нажали «Начать» — поднимается отдельная сессия агента по этой задаче, карточка уезжает в «В работе».
- **Продолжать в том же чате.** У задачи ровно одна сессия на всю её жизнь. Как только сессия есть, кнопка становится «Продолжить» и открывает прежний чат, а не заводит новый. Перед отправкой видно заготовку сообщения — её можно переписать, уйдёт то, что осталось в поле.
- **Показывать задачу в чате.** В сессии, поднятой с доски, в шапке виден чип задачи с текущей колонкой.

## Установка

```bash
dsh plugin --profile web add @goodandready/dsh-kanban
```

Из локальной рабочей копии:

```bash
dsh plugin --profile web add file:/путь/к/dsh-kanban
```

Перезапустите веб-интерфейс и обновите страницу с очисткой кэша.

Других плагинов не требует: клиент Gitea у канбана свой. Пока адрес инстанса не задан, доска работает, а импорт честно объясняет, чего не хватает.

## Настройка

**Настройки → Плагины**, карточка **Канбан**.

| Поле | Что задаёт |
|---|---|
| Адрес инстанса | `https://gitea.example.com`. Пусто — импорт недоступен. |
| Имя учётной записи | ИМЯ учётной записи DSH с токеном, по умолчанию `GITEA_TOKEN`. Сам токен сюда не вводить. |
| Корень проектов | Где лежат рабочие копии. Пусто — рабочая папка харнесса. |
| Шаблон первого сообщения | Текст, с которого начинается сессия. Пусто — встроенный. Подстановки: `{repo}`, `{issueNumber}`, `{title}`, `{body}`, `{issueUrl}`. |
| Метки колонок | Имя метки Gitea для «В работе», «Ревью», «Deploy», «Cleanup». Пусто — метка не ставится. |
| Пределы колонок | Предел числа карточек. Ноль — без предела. |

Токен в настройках **не хранится**: там только ИМЯ учётной записи, а сам секрет лежит в хранилище учётных данных DSH. Наружу значение не отдаётся никогда, включая сообщения об ошибках. Если у вас уже настроен `GITEA_TOKEN` для других плагинов, достаточно вписать адрес инстанса.

Все поля настроек скалярные. Это не упрощение, а требование: клиентский API настроек пишет только скаляры, и словарь или массив сделал бы карточку нередактируемой. Доски поэтому живут в хранилище задач, а не в настройках.

## Колонки

| Колонка | Признак входа |
|---|---|
| Backlog | issue есть, никто не взял |
| В работе | сессия поднята, в issue есть стартовый комментарий с планом и веткой |
| Ревью | PR снят с WIP, ревьюер даёт PASS/FAIL |
| Deploy | PR влит в `main`, ждём согласованный deploy и production-проверку |
| Cleanup | ветка в Gitea, worktree и локальная ветка ещё не удалены |
| Done | issue закрыт **и** cleanup записан в итоговом комментарии |

Колонка `cleanup` не лишняя: по воркфлоу задача не завершена, пока cleanup не сделан и не записан. Доска, отправляющая карточку в `done` по merge, врёт ровно там, где копятся забытые ветки.

WIP PR **не** двигает карточку в «Ревью»: он открывается рано и означает «работа идёт», а не «смотрите».

Превышение предела колонки подсвечивается, но перенос не запрещает: предел — ориентир, а не преграда.

## Чего плагин не делает

- **Не создаёт ветки и worktree.** По воркфлоу агент сначала делает preflight — смотрит открытые ветки и worktree, проверяет рабочее дерево — и только потом заводит worktree от свежего `origin/main`. Ветка, созданная заранее, обессмысливает preflight.
- **Не пишет стартовый комментарий в issue.** Его пишет агент после preflight, потому что до preflight ветка и план неизвестны.
- **Не подсказывает имя ветки** в первом сообщении: его выбирает агент.
- Ветка и worktree на карточке — **наблюдение**, а не намерение.
- Не трогает Hermes Kanban. Это другая система.

## Хранилище

`<DSH_HOME>/kanban/kanban.db`, где `DSH_HOME` — переменная окружения либо `~/.dsh`. SQLite через встроенный `node:sqlite`; внешних зависимостей нет.

Порядок карточек хранится дробным индексом: перетаскивание — всегда один `UPDATE` одной строки, сколько бы карточек ни было в колонке.

## Автоперемещение

Карточки двигаются сами. Три источника со строгим приоритетом — **Gitea > инструмент агента > жизненный цикл сессии**. Без приоритета «PR влит → deploy» через секунду перебивалось бы «ход завершился → в работе», и карточка прыгала бы.

| Наблюдение в Gitea | Колонка |
|---|---|
| есть ветка по задаче | В работе |
| PR открыт и снят с WIP | Ревью |
| PR влит | Deploy |
| issue закрыт, ветка ещё есть | Cleanup |
| issue закрыт, ветки нет | Done |

Каждый переход попадает в журнал задачи с источником и пояснением: `Ревью ← gitea · PR #39 снят с WIP`. Когда доска однажды покажет не то, будет видно, кто её подвинул.

### Ручной перенос — это команда агенту

Карточку двигают не ради учёта. Человек перетащил — значит просит запустить тот этап, куда перетащил, и команда уходит в чат задачи отдельным сообщением. При отпускании карточки доска показывает окно с описанием последствий; отмена оставляет карточку на месте.

| Куда перенесли | Что происходит |
|---|---|
| Backlog | работа останавливается: идущий ход агента прерывается |
| В работе | агент начинает или продолжает реализацию |
| Ревью | агент снимает с PR пометку черновика и запрашивает проверку |
| Deploy | агент вливает PR и выкатывает |
| Cleanup | агент удаляет ветку, worktree и локальную ветку |
| Done | завершение; сюда переносит только человек |

**Перенос в Deploy и есть явное «ок» на выкатку.** Воркфлоу требует разрешения человека перед deploy, и это разрешение дано движением, а не словом в чате — второй раз агент не спрашивает.

Инструменту агента переход в `done` закрыт и даже не предлагается в перечислении. Его путь к завершению — закрыть issue и удалить ветку; сверка с Gitea сама увидит закрытый issue без ветки. Карточка двигается фактом, а не заявлением.

**Признак «нужен человек».** Колонки «Блокировано» в наборе нет, поэтому запрос разрешения или вопрос агента не двигают карточку, а поднимают на ней оранжевую точку. Признак снимается сам, когда ход возобновляется.

**Инструмент агента** `board_move` выключен по умолчанию: скилл `gitea-project-workflow` пока запрещает этому CLI трогать канбан.

Определение инструмента живёт в `lib/board-tool.js` отдельно от обвязки cordis и
следует контракту `defineTool` из `@deepseek-ai/dsh-tools` **не ниже 0.1.0-rc.8**:
`output` обязателен, а `parameters` — карта «имя -> схема значения», а не JSON
Schema с корнем `type: 'object'`. Пропущенный `output` роняет не инструмент, а
загрузку всего профиля, поэтому форма закреплена тестами `test/board-tool.test.mjs`.

## Синхронизация

**Gitea → канбан.** Опрос с настраиваемым промежутком плюс вебхук для мгновенной сверки. Вебхук — ускорение, а не замена: он может быть не настроен, недоступен снаружи или потерян, и опрос остаётся всегда.

Маршрут вебхука `/dsh-kanban/webhook`, подпись проверяется общим секретом. **Без секрета вебхук не принимается вовсе** — иначе карточки двигал бы кто угодно снаружи.

**Канбан → Gitea.** Перенос карточки ставит метку колонки, `Done` дополнительно закрывает issue. Чужие метки не трогаются: `bug`, `feat`, `hotfix` принадлежат процессу, и стирать их доска права не имеет. Свои метки `kanban/*` заводятся автоматически, если их в репозитории ещё нет.

Отправка идёт очередью: перенос карточки не ждёт сети, доска работает и при недоступном Gitea. Неудачная отправка повторяется, а исчерпав попытки — попадает в журнал задачи, а не исчезает.

**Конфликты.** Если обе стороны изменились с последней сверки, побеждает более позднее изменение, а проигравшее **называется в журнале задачи**. Синхронизация, тихо отменяющая правку человека, хуже отсутствующей: расхождение остаётся, а узнать о нём неоткуда.

До первой сверки «изменилось с прошлого раза» смысла не имеет — прошлого раза не было, — поэтому первая сверка принимает положение дел, а не спорит с ним.

## Ограничения

- Точного «работа идёт прямо сейчас» инстанс не знает. Порядок репозиториев и вывод колонок — приближение по открытым задачам, веткам и времени правки.
- Клиент Gitea покрывает только нужное доске: issue, PR, ветки, метки, поиск репозиториев.
- Неполное наблюдение считается отсутствующим: репозиторий, который не прочитался целиком, пропускается до следующей сверки. Иначе непрочитанные PR выглядели бы как их отсутствие и утаскивали карточку назад.
